# ADR 0023：小鹤音形精准匹配提示合同

- 状态：Accepted（2026-08-20 修订）
- 日期：2026-08-05
- 决策范围：`xiaohe-yinxing` 无精确命中时的部分匹配提示
- 替代关系：补充并局部替代 ADR 0022 中“词组只按完整精确编码出现”的绝对限制；四码提交、真实重码和小鹤双拼隔离合同不变

## 背景

产品经理确认：输入 `un` 等当前未命中任何完整词条的编码时，可以提示词库里编码以 `un` 开头的词；候选必须按词库给出的顺序显示，而不是按拼音、频率或学习结果排序。只有当前编码未精确命中时才显示这类编码提示，因此该规则命名为“精准匹配提示”。提示数量应交给用户设置，最多 9 项。

2026-08-20 客户进一步确认：空码时只需要源序第 1 项后续提示，不需要 9 项，数量固定且不做设置选项。本修订替代下文原数量设置结论，不改变精确候选、排序或提交边界。

## 决策

正式 `xiaohe-yinxing` 查询按以下互斥顺序执行：

1. `rawCode` 为空时不查询、不枚举全表。
2. 任一启用分类存在当前编码精确词条时，锁定精确路径，只返回经过分类和用户规则处理后的同码候选。
3. 系统精确路径被 `#删` 清空时仍保持锁定，不回退到部分匹配提示。
4. 只有不存在系统精确词条且不存在当前编码的用户精确规则时，才收集编码严格长于 `rawCode` 的前缀词条作为提示。
5. 提示依次按分类显式顺序和分类内持久化 `source_order` 合并；相同文字稳定去重。禁止拼音排序、基础频率重排和用户学习重排。
6. 引擎和 UI 的提示上限固定为 1；设置页不提供数量选项。该限制不截断真正的精确同码候选。
7. 候选栏显示文字和“尚未输入的编码后缀”，例如输入 `un` 时把完整编码 `unjb` 显示为“伤脑筋 jb”。
8. 提示项允许用户主动选择并提交；提示集合不得参与唯一候选自动上屏、第五键顶屏、有效完整码判定或正向/反向空码切分。
9. 不存在精确词条也不存在有效更长编码时，仍按既有真空码合同处理。

## 用户规则

- `#删` 继续按“完整编码＋文字”作用于提示，并从源序列表中移除对应项；删除后由后续源序项自然补位。
- 普通用户词可以在系统提示之后补充缺失文字，但不得越过系统源序提示。
- `#固/#N` 不重排提示集合；它们只对合法精确候选的稳定顺序生效。
- 用户学习不参与提示排序。

## 兼容与后果

- Rust 内部仍可复用现有候选协议，因此不增加 C ABI、Node-API 或 ArkTS Native 字段，interface/ABI version 保持 4。
- UI 由当前 `rawInput` 与候选完整 `reading` 识别提示并显示后缀；精确候选保持原文展示。
- 2026-08-05 的 schema 3 曾新增 `xiaoheYinxingHintCandidateCount`；2026-08-20 修订已退出该字段的读取、写入和 UI，历史持久化值被忽略，不需要新增迁移版本。
- 正式 bundle、分类顺序、`source_order` 和用户词库文件格式不变；`xiaohe` 小鹤双拼完全隔离。
- ADR 0022 的“一至三码不自动提交”“四码只用精确候选自动提交/选重”和“不得把前缀预览用于自动决策”继续有效；仅“无精确时不显示词组前缀”由本 ADR 的有界提示规则替代。
